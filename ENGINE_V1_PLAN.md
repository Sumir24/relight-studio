# Relight Studio — Universal Image Relighting Engine Architecture

## Product boundary

Relight Studio is a general-purpose 2.5D virtual lighting studio for existing photographs. The source photograph remains the final output canvas; geometry is an internal representation used to estimate how lighting should change. The engine must not be designed around one photograph or one scene category.

The same renderer and shared scene-buffer contract must support portraits, group photographs, products, food, interiors, architecture, landscapes, street scenes, vehicles, animals, macro photographs, still life and other ordinary photographic content. These are benchmark domains, not separate engines.

## Core architectural rule

**Scene understanding is adaptive; lighting physics and image reconstruction are shared.**

- The renderer does not branch on names such as `mountain`, `water`, `face`, `car`, or `sofa`.
- Segmentation labels are open-vocabulary strings discovered from the image or supplied by the user.
- No semantic class is globally protected or globally lightable by default. The neutral default considers all visible pixels as candidates, then applies geometry confidence, explicit protection masks, material response, and user policy.
- Domain hints may select extra analysis passes or priors, but may not alter coordinate conventions, scene-buffer meaning, or the core lighting equations.
- Model outputs must carry provenance and uncertainty; missing information must remain missing rather than be fabricated.

## Shared scene contract

Every engine pass consumes camera-aligned buffers on one pixel grid:

- Original RGB source in sRGB; rendering calculations are performed in linear light.
- Optional original alpha/transparency mask, retained separately and restored after rendering.
- Positive camera-Z depth, depth confidence, and declared unit kind (`metric` or `relative`).
- Camera intrinsics and one coordinate convention: +X right, +Y up, +Z away from camera.
- Camera-space surface normals derived from the same depth buffer or a compatible estimator.
- `lightable_mask` and optional `protected_mask`, generated by a neutral semantic policy or explicit user edits.
- Dynamic semantic class masks and per-instance masks retained in the shared scene buffers for later material assignment, editability and response passes.
- Arbitrary semantic class masks and independently addressable instance masks, e.g. one combined `person` class plus `person__001`, `person__002`, `leather_bag__001`, `glass_bottle__001`, `cat__001`, or any open-vocabulary object label.
- Optional roughness, metalness and dielectric specular maps, each marked as model-estimated, user-authored, generic prior, or unavailable.
- Optional per-pixel material/response class, transparency, emissive and environment/reflection masks when those estimators are available. These describe reusable material families, not scene categories.

No stage may silently substitute a different depth frame, axis convention, resize, crop or camera model.

## Runtime graph

1. **Input normalization** — EXIF orientation, ICC-to-sRGB conversion, alpha preservation, image dimensions, source metadata and a consistent RGB tensor. (Implemented for the raster formats supported by Pillow.)
2. **Adaptive scene discovery** — image-level caption and dense region descriptions propose image-specific concepts. Current candidate: Florence-2 Base for detailed captions and dense-region labels. User prompts and manual masks can override or supplement discovery.
3. **Open-vocabulary mask construction** — candidate labels/boxes are converted into dynamic class masks and separate instance masks. Current code path: Grounding DINO Tiny + SAM 2.1 Hiera Tiny. Masks retain source labels and per-instance identity; no fixed class taxonomy is required.
4. **Geometry estimation** — monocular depth plus confidence; derive camera-aligned point maps and normals from the same registered depth map. Current adapter: Depth Anything V2 Small. New evaluation candidate: Depth Anything 3 Small/Base, with checkpoint and API validation before adoption.
5. **Scene-domain hinting** — optional classification such as portrait/product/interior/landscape. Hints are advisory QA metadata and can select additional estimators; they do not change the renderer contract.
6. **Source-light model** — current path requires user-supplied source-key direction, strength, approximate colour temperature and ambient contribution. Future path estimates illumination with confidence and exposes correction controls.
7. **Material/response estimation** — estimate or edit diffuse/roughness/specular/metalness, plus special response types (transparent, transmissive, reflective, emissive, subsurface) where supported. Unknown material must remain unknown or use a clearly marked conservative prior.
8. **Target virtual rig** — directional, point and rectangular-area lights with normalized or metric positions according to depth units, size, colour, power and shadow controls.
9. **Shared surface response** — Lambertian diffuse and GGX microfacet specular baseline, extended with material-aware response branches. The core model is reusable across every scene category; material response, not scene name, determines the shading behaviour.
10. **Visibility** — depth-guided 2.5D ray visibility for approximate cast shadows. This is limited to visible first-surface geometry and cannot recover hidden backsides or true overhangs.
11. **Source-preserving reconstruction** — transfer target/source illumination to low-frequency image components while preserving high-frequency texture; add incremental specular energy; blend by geometry/material confidence and user protection masks.
12. **Quality gate** — no-op invariance, light movement, surface-orientation response, material response, shadow direction, edge leakage, highlight clipping, texture retention, deterministic repeatability, and cross-domain benchmark checks.

Material response is a separate extensible layer from scene classification. See `MATERIAL_RESPONSE_ROADMAP.md` for reusable diffuse, conductor, layered, subsurface, transmissive, emissive and environment-dependent families.

## Adaptive scene understanding

### No fixed landscape prompt list

Scene concepts are discovered per image. The scene-discovery adapter may produce labels such as `person`, `skin`, `hair`, `shirt`, `glass bottle`, `metal cap`, `ceramic plate`, `food`, `sofa`, `window`, `ceiling`, `car`, `dog`, `tree`, `water`, or concepts not known in advance. The adapter must return dynamic labels; it must not map all content into a small hand-written list.

### Semantic policy

`SemanticRoutingPolicy` takes optional `protected_labels` and optional `lightable_labels`:

- Default `protected_labels=()`.
- Default `lightable_labels=None`, meaning all visible pixels are candidates subject to geometry/material confidence.
- Explicit protected labels exclude selected image regions.
- An explicit lightable-label allow-list narrows the target surface set.
- The user can add, subtract, soften or refine masks. The system must record edits.

This is intentionally neutral. Later material estimators may recommend special handling for water/glass/skin/metal, but labels alone must not trigger unverified physical behaviour.

## Domain coverage and validation matrix

The engine must be validated against a matrix, not declared universal after passing one landscape:

| QA domain | Representative difficult cases |
|---|---|
| Portrait | skin gradients, hair strands, glasses, ears, clothing boundaries |
| Group photo | overlapping people, occlusion, mixed depths, varied skin/clothing |
| Product | glossy packaging, transparent glass, metallic edges, white backgrounds |
| Food | irregular surfaces, oils, liquids, fine garnish |
| Interior | furniture overlap, windows, mirrors, mixed artificial/daylight |
| Architecture | repeated edges, glass facades, large planar surfaces |
| Landscape | foliage, water, sky, distant mountains, thin branches |
| Street | vehicles, people, signs, shadows, reflections |
| Vehicle | curved paint, windows, chrome, tyres |
| Animal | fur, whiskers, eyes, overlapping limbs |
| Macro | shallow depth of field, translucent details, fine texture |
| Still life | multiple materials and small objects |
| Artwork | stylized shading, illustration, painted texture |
| Other | unusual or mixed scenes not covered by the above |

The table is a required test plan, not a promise that every image can be physically reconstructed. Unsupported/ambiguous regions must be surfaced with low confidence and left to user review.

## Geometry, coordinates and scale

- Camera coordinates: +X right, +Y up, +Z away from camera.
- A directional-light vector points from a receiving surface toward the light source.
- Camera intrinsics must be calibrated or recorded as an assumption.
- Relative depth is a shape cue, not metres. Point/area light positions and attenuation are normalized scene-space approximations until metric scale is calibrated.
- Metric point/area behaviour requires a metric-depth estimator that is validated for the relevant image domain, or explicit scene-scale calibration.
- Geometry confidence must down-weight depth discontinuities, textureless/reflective/transparent surfaces, and regions where model estimates are unstable.

## Current implementation status

- Typed, validated camera/scene/light/rig/settings contracts, including optional alpha preservation.
- Input decoding with EXIF orientation, embedded ICC conversion to sRGB and separate alpha preservation.
- Camera-space depth back-projection and depth-derived normals.
- Directional, point and rectangular-area light models.
- Lambertian diffuse and GGX specular response.
- Approximate camera-projected 2.5D depth-ray visibility.
- Source-to-target shading transfer with detail retention, confidence/mask blending and highlight protection.
- Depth Anything V2 Small relative-depth adapter; output polarity is explicit.
- Florence-2 Base scene-discovery adapter for detailed captions and dense region labels (implemented; neural inference not executed in this environment).
- Grounding DINO Tiny + SAM 2.1 Hiera Tiny adapter now accepts arbitrary image-specific prompts and returns dynamic masks.
- Generic semantic policy has no hardcoded sky/water/mountain/person/product rules.
- Camera FOV calibration, explicit user source-light calibration and user-authored material overrides.
- Scene-analysis and relighting CLIs with provenance reports.
- Structural scene QA report detects invalid/flat depth, low confidence, absent/degenerate normals, missing geometry confidence, suspicious mask coverage and near-duplicate instances.
- Arbitrary-image input preflight and multi-image scene-analysis benchmark runner; case labels remain report metadata and do not select renderer branches.
- Synthetic cross-label policy tests across portrait/product/interior/animal/vehicle-like concepts.

## Model evaluation notes

- Florence-2 Base is a compact candidate for image captions and dense-region labels; the official Hugging Face model card lists MIT and documents captioning, object detection, dense-region captioning and phrase grounding. Its custom-code loading path requires a pinned and audited revision.
- Grounding DINO's official repository identifies Apache-2.0; SAM 2's official repository identifies the model checkpoints and code as Apache-2.0.
- Depth Anything 3's official repository identifies Apache-2.0 for its code and lists DA3-SMALL/BASE as Apache 2.0 checkpoints. Its DA3 Metric Large and DA3 Mono Large checkpoints are also listed Apache 2.0; the larger DA3 variants are CC BY-NC 4.0. Evaluate DA3-Small/Base against existing DA2 Small before replacement.
- SAM 3 is not the default product dependency because its official repository uses a separate SAM License rather than Apache-2.0; legal review is required before commercial adoption.

## Remaining engineering milestones

1. Run the current model stack on a multi-domain benchmark set, not only the original landscape. The runner is implemented; the neural model execution is pending.
2. Execute Florence-2 discovery + Grounding DINO/SAM2 masks on portraits, products, interiors and mixed scenes; audit misses, duplicates and fine boundaries.
3. Evaluate Depth Anything 3 Small/Base against Depth Anything V2 across all benchmark domains; confirm exact checkpoint revisions and outputs before switching.
4. Add material/response estimators for skin, hair, fabric, wood, stone, plastic, glass, metal, liquid, emissive and reflective surfaces, each with uncertainty and manual override.
5. Estimate source illumination from the original photo and allow user correction.
6. Improve depth-edge handling, layered occlusion, contact shadows and approximate hidden-surface completion.
7. Add dedicated response paths for transparent/transmissive/reflective/emissive surfaces rather than hardcoding their semantic names.
8. Establish real-photo ground truth and cross-domain quality benchmarks; synthetic tests alone do not establish visual quality.
9. Profile CPU/MPS/GPU and worker execution while preserving one shared scene-buffer schema.

## Explicit non-claims

- A general-purpose engine does not imply every single image can be physically relit perfectly.
- Relative depth is not metric distance.
- FOV-derived intrinsics are approximate unless independently calibrated.
- Florence-2 dense region descriptions are candidate concepts, not exhaustive ground truth.
- Prompt-grounded masks are not universal segmentation ground truth.
- Source light remains user-calibrated in this build, not automatically inferred.
- Material values are user overrides or generic priors, not verified neural estimates.
- 2.5D geometry does not recover unseen surfaces.
- Neural adapters have not yet been executed on the uploaded photograph or a multi-domain real-photo benchmark in this environment.
